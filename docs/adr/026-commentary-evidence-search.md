# ADR-026: Bound the planned evidence-seeking agent's commentary search in code: one read-only tool

*Status: Proposed · Date: 2026-11-15, spending protection 2026-11-16 · Decider: Erhan (+ AI-assisted analysis)*

## Context
Use case UC2 of the Change Analyst, seeking missing evidence, has an agent recognise a gap in the evidence, run at most two further search rounds with read-only tools under a guardrail, and return either a completed answer or a precisely named evidence gap. The fixed pipeline of [ADR-025](025-commentary-retrieval.md) sends one question's top 5 passages to the model without tools; on the dev case D1 the gold evidence ranked 6 and 7 and stayed out of the context ([generation evidence](../evidence/2026-11-15-commentary-generation.md)). Once a model chooses its own queries, nothing it writes may widen the editions selected for the question, the number of passages it receives, the number of searches, or its reach beyond the public commentary passages.

## Decision
The agent gets exactly one tool, `search_commentary` (`tools/commentary_rag/evidence_search.py`), and every bound of it is code, not model choice: the model supplies only a query, what it is seeking and optionally a narrower selection of the question's editions; code fixes the ranking (the hybrid RRF of ADR-025 over the selected editions only), a top-10 window, at most `min(5, remaining capacity)` new passages per search, at most 10 distinct passages per question including the fixed five, and at most two search rounds, which refused and failed requests use too. Malformed, out-of-scope and repeated requests are refused without ranking, a failed ranking is reported to the model as a tool error instead of raised, and results return as the same escaped, untrusted passage data as the fixed context. The agent's loop for one question (`evidence_agent.py`) sends the Phase 2 request content and system prompt with a short, generic instruction to search for what the passages do not state, offers only this tool, grows the conversation only by appending (each assistant turn as returned, then the tool result for its tool-use ID), allows at most three generation calls, offers no tool on the last call or once the searches or the passage budget are used up, accepts an answer only when it matches the schema and cites only passages supplied to the model, and retries nothing. One monotonic deadline per question is enforced cooperatively: it is checked before and after token counting, generation and search, and bounds every request's timeout. Only structured metadata (outcomes, codes, passage IDs, ranks, scores, hashes, counts, usage) is publishable; raw requests, responses, queries, seeking text, error text and passage text stay in local artifacts. Every call of the loop is accounted, and its entry point cannot be called without the books: USD 100 is one aggregate limit for Phase 2 and Phase 3 together. The historical Phase 2 ledger (`results/generation-ledger.jsonl`) stays byte-identical and counts with everything it committed (USD 1.930804, SHA-256 `e0d031ac…`); one active ledger, `phase3-ledger.jsonl`, sits beside it for all later spending, whatever the question or condition, and its first entry pins the historical ledger's hash and committed amount and the limit. The folder, the ledger names, the historical ledger's SHA-256 (a caller may only repeat it), the limit, the Phase 2 settings that set a ceiling and the prices of `pricing.json` are code, not arguments. Phase 2's prices, cost calculation, reserve and settle events and exclusive folder lock are reused; the lock is held for the whole question. The ceiling is the agent's own, one calculation for admission and every reservation: the counted input with a 10 % margin, every token at the dearest input rate of `pricing.json` (an hour's cache write, although the request asks for no caching), plus the full output allowance, times the 1.1 US data-residency multiplier, computed exactly and rounded up to a micro-dollar, so that any usage the settlement prices within the margin fits its reservation. A question is admitted only when its worst case fits: three calls at an input cap of 80,000 counted tokens, each at its ceiling (USD 1.4784, so USD 4.4352 in all). Each call is counted, refused above the cap, saved, reserved under a stable call ID, checked against the deadline once more (a request it stops is recorded as never sent, which releases it), sent once, saved as returned and settled: at the cost of its validated usage (`output_tokens`, which includes thinking), or at its whole reservation as committed exposure when nothing can be priced (a timeout, a lost connection, an error response, missing or unreadable usage, another model or price tier). A cost above the reservation is recorded uncapped and ends the question before any further call. Settling never decides acceptance: late, invalid and rejected responses are settled and still not accepted. A failed write stops the question and leaves a sent call, or one whose release was not saved, reserved, and the record claims a settlement or release only once the ledger holds it; damaged or changed books (an emptied ledger, a call ID that does not name its case, a settlement that contradicts its basis or the cost of its saved usage included) are refused as they are, and the books are used by their canonical paths, so a link from another folder cannot move the folder lock; a question already in the ledger is never sent again. Ledger and record carry codes, counts, hashes and amounts only; provider strings such as the stop reason and the returned model become allowlisted codes. Neither module reads the tariff database or computes or changes a tariff value. ADR-025's fixed, no-tools pipeline is unchanged and stays the baseline.

## Alternatives weighed
- **A fixed Top-10 context only**: no agentic behaviour; kept instead as the control of the planned comparison (on the eight dev cases it already covers all 15 gold items).
- **Limits, ranking or editions chosen by the model**: model output could widen the evidence set; fixed bounds can be tested without a model.
- **A framework harness (LangGraph, LlamaIndex) or several agents**: new dependencies and orchestration for one tool and two rounds.
- **More tools from the start**: no concrete scenario needs a second tool yet; one is added only when one does.
- **A hard wall-clock limit through a separate process or supervisor**: a new runtime harness; this increment documents the weaker, cooperative guarantee instead.
- **A separate budget for Phase 3, or a ledger per case or condition**: each new file would start from nothing and could raise the total spent; one active ledger beside the pinned historical one keeps one limit.
- **Settling error responses at zero, as Phase 2 does**: an error response reports no usage, and the agent counts only validated usage as cost, so it keeps the reservation instead.

## Consequences
- (+) Every bound, refusal and protocol rule is enforced and tested offline: the tool at its own seam, the loop at the provider's HTTP boundary with the real client, a fake key and a controllable clock ([§13](../arc42/13-test-strategy.md)).
- (+) A passage's instruction-like text reaches the model only as escaped data; offline this shows containment, not how a real model responds to it.
- (-) The passage budget equals a fixed Top-10 context in maximum distinct-passage count only, not in token volume, compute or cost; the agent adds model calls.
- (-) The deadline is cooperative, not a hard wall-clock limit: a check cannot interrupt a request already sent or a search in progress, and the HTTP client's timeouts bound each phase of a request rather than the whole, so a question can overrun its budget by the operation in progress. Stronger cancellation is open.
- (+) The spending rules are tested offline at the same seam with temporary ledgers and artifact folders: the exact admission boundary, the input cap, the dearest priced usage at the margin against its reservation, three calls of one question within the shared limit, every sent call settled once, exposure kept where usage is missing, a cost above the reservation, failed writes before and after sending (the pin, the reservation, a release and a settlement among them, simulated so that they fail the same way for any user), a concurrent invocation (also through a link to the active ledger from another folder) and a repeated one, damaged and changed books (settlements that contradict their saved usage and call IDs that do not name their case among them), altered historical bytes whatever hash the caller gives, and public records free of provider text.
- (-) Not ready for live use: the provider has never seen this request shape (a strict tool, the answer format beside tools, `tool_choice` none, replayed thinking blocks) nor sent the usage the validator expects, and there is no runner and no evaluation. If live responses carry a usage field the validator rejects, every call settles at its whole reservation; the first live step should inspect one response's usage. The first evaluation run needs its own cost plan within the aggregate limit.
- (-) The aggregate limit holds for spending through the agent's entry point, which so far serves only the agent condition: the fixed Top-5 and Top-10 conditions do not yet use the shared accounting path, since the Phase 2 runner neither counts the historical ledger nor writes the active ledger's events, and the runner increment must give them one. The Phase 2 runner must not be used to bypass that path during Phase 3: it still checks its own ledger only, and a new Phase 2 run would change the historical ledger, after which the agent refuses to run. The limit bounds what is admitted and reserved, and the ceiling is the application's calculation from recorded prices, not a bound the provider's billing guarantees: a call costs more than its reservation only when its usage goes beyond the margin (input the count underestimated by more than 10 %) or its billing beyond `pricing.json`, and then that one call's overrun can take the total past USD 100. The books cannot be moved: another folder, a second ledger file, another limit or a lower margin is refused before anything is counted, and prices cannot be passed in. A change to `pricing.json` itself changes the ceiling, and an earlier usage settlement whose tokens the changed rates price differently then reads as damaged (its cost no longer matches its saved usage), so the agent refuses until the change is decided. The active ledger is append-only by convention: whole lines removed from its end cannot be told from the file alone, so it needs the same protection as the recorded ledger (version control).
- (-) Reservations are larger than Phase 2's for the same count (USD 0.71852 instead of 0.646604 at 1,500 counted tokens), so fewer questions are admitted near the limit. A cost above the reservation is recorded in full and stops the question; a final answer is still accepted then, so a runner must also read the flag, not only the outcome.
- (-) A write error raised only after the whole line reached the ledger (on closing the file) leaves that line in force, a truthful settlement at the calculated cost or a release of a request never sent, while the question still ends as a persistence error; a line cut short makes the ledger damaged, and every later question is refused until it is repaired by hand. Detecting the first case would need recovery logic this increment does not build.
- (-) A question whose reservation was released as never sent still has its ID in the ledger and is refused when run again; a retry, if authorised, needs a new case ID. There is no automatic recovery or retry.
- (-) The modules reuse private helpers of the generation module (the passage renderer, the request hash), so a change there changes them; the pilot's CI job catches it. Revisit when the evaluation shows a fixed Top-10 context recovers the same evidence at lower cost, or a case needs a second tool.

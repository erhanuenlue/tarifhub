# ADR-026: Bound the planned evidence-seeking agent's commentary search in code: one read-only tool

*Status: Proposed, evaluated (acceptance open, see Decision status) · Date: 2026-11-15, spending protection 2026-11-16, one-question runner 2026-11-18, first live run recorded 2026-11-20, comparison conditions 2026-11-21 (offline), comparison run 2026-11-21, blinded review confirmed 2026-11-22 · Decider: Erhan (+ AI-assisted analysis)*

## Context
Use case UC2 of the Change Analyst, seeking missing evidence, has an agent recognise a gap in the evidence, run at most two further search rounds with read-only tools under a guardrail, and return either a completed answer or a precisely named evidence gap. The fixed pipeline of [ADR-025](025-commentary-retrieval.md) sends one question's top 5 passages to the model without tools; on the dev case D1 the gold evidence ranked 6 and 7 and stayed out of the context ([generation evidence](../evidence/2026-11-15-commentary-generation.md)). Once a model chooses its own queries, nothing it writes may widen the editions selected for the question, the number of passages it receives, the number of searches, or its reach beyond the public commentary passages.

## Decision
The agent gets exactly one tool, `search_commentary` (`tools/commentary_rag/evidence_search.py`), and every bound of it is code, not model choice: the model supplies only a query, what it is seeking and optionally a narrower selection of the question's editions; code fixes the ranking (the hybrid RRF of ADR-025 over the selected editions only), a top-10 window, at most `min(5, remaining capacity)` new passages per search, at most 10 distinct passages per question including the fixed five, and at most two search rounds, which refused and failed requests use too. Malformed, out-of-scope and repeated requests are refused without ranking, a failed ranking is reported to the model as a tool error instead of raised, and results return as the same escaped, untrusted passage data as the fixed context. The agent's loop for one question (`evidence_agent.py`) sends the Phase 2 request content and system prompt with a short, generic instruction to search for what the passages do not state, offers only this tool, grows the conversation only by appending (each assistant turn as returned, then the tool result for its tool-use ID), allows at most three generation calls, offers no tool on the last call or once the searches or the passage budget are used up, accepts an answer only when it matches the schema and cites only passages supplied to the model, and retries nothing. One monotonic deadline per question is enforced cooperatively: it is checked before and after token counting, generation and search, and bounds every request's timeout. Only structured metadata (outcomes, codes, passage IDs, ranks, scores, hashes, counts, usage) is publishable; raw requests, responses, queries, seeking text, error text and passage text stay in local artifacts. Every call of the loop is accounted, and its entry point cannot be called without the books: USD 100 is one aggregate limit for Phase 2 and Phase 3 together. The historical Phase 2 ledger (`results/generation-ledger.jsonl`) stays byte-identical and counts with everything it committed (USD 1.930804, SHA-256 `e0d031ac…`); one active ledger, `phase3-ledger.jsonl`, sits beside it for all later spending, whatever the question or condition, and its first entry pins the historical ledger's hash and committed amount and the limit. The folder, the ledger names, the historical ledger's SHA-256 (a caller may only repeat it), the limit, the Phase 2 settings that set a ceiling and the prices of `pricing.json` are code, not arguments. Phase 2's prices, cost calculation, reserve and settle events and exclusive folder lock are reused; the lock is held for the whole question (one cell: a comparison takes it for each cell). The ceiling is the agent's own, one calculation for admission and every reservation: the counted input with a 10 % margin, every token at the dearest input rate of `pricing.json` (an hour's cache write, although the request asks for no caching), plus the full output allowance, times the 1.1 US data-residency multiplier, computed exactly and rounded up to a micro-dollar, so that any usage the settlement prices within the margin fits its reservation. A question is admitted only when its worst case fits: three calls at an input cap of 80,000 counted tokens, each at its ceiling (USD 1.4784, so USD 4.4352 in all). Each call is counted, refused above the cap, saved, reserved under a stable call ID, checked against the deadline once more (a request it stops is recorded as never sent, which releases it), sent once, saved as returned and settled: at the cost of its validated usage (`output_tokens`, which includes thinking), or at its whole reservation as committed exposure when nothing can be priced (a timeout, a lost connection, an error response, missing or unreadable usage, another model or price tier). A cost above the reservation is recorded uncapped and ends the question before any further call. Settling never decides acceptance: late, invalid and rejected responses are settled and still not accepted. A failed write stops the question and leaves a sent call, or one whose release was not saved, reserved, and the record claims a settlement or release only once the ledger holds it; damaged or changed books (an emptied ledger, a call ID that does not name its case, a settlement that contradicts its basis or the cost of its saved usage included) are refused as they are, and the books are used by their canonical paths, so a link from another folder cannot move the folder lock; a question already in the ledger under the same condition is never sent again. Ledger and record carry codes, counts, hashes and amounts only; provider strings such as the stop reason and the returned model become allowlisted codes. Neither module reads the tariff database or computes or changes a tariff value. ADR-025's fixed, no-tools pipeline is unchanged and stays the baseline. For the Phase 3 comparison (2026-11-21, built and tested offline) the same loop and books serve three conditions fixed in code and chosen by name: A (`fixed5`) and B (`fixed10`) send that Phase 2 request with the question's hybrid top 5 or top 10, once and without any tool, admitted at one call's ceiling; C (`agent`) is the loop above. Every ledger event carries its condition and every call the ID `<case>-<condition>-call<n>`, so the identity in the books is the case and its condition (entries written before conditions existed, the D1 run's, are the agent's), and a call ID an older reservation holds is never written twice. Every reservation also records the question's SHA-256 and the sorted editions, so one case ID names one question over one edition selection: a case booked before with another is refused under any condition. The comparison runner (`run_comparison.py`) reads only each case's ID, question and editions; before the model loads it refuses a matrix whose worst case does not fit beside everything committed and a case whose cells in the books were asked something else or recorded no question (the D1 run recorded none); every cell's admission, under the lock, also holds back the worst case of the matrix's cells still to run after it, so after a booking by another invocation in between, the matrix stops at the next cell once the rest no longer fits; it ranks every case before any cell runs, gives A, B and C the top 5, 10 and 5 of the case's ranking with the same time budget per cell, stops after a cell that needs a person, and keeps the outputs of every cell that ended even when an unexpected error stops it; its offline `plan` reads the books without the lock, states the assumptions of its bounds and each case's pairing, and sends and writes nothing.

## Alternatives weighed
- **A fixed Top-10 context only**: no agentic behaviour; kept instead as condition B of the comparison (on the eight dev cases it already covers all 15 gold items).
- **The fixed conditions through the Phase 2 runner**: it checks its own ledger only and a new run would change the historical ledger; the fixed conditions use the agent's books instead.
- **The condition inside the case ID only** (such as `E1.A`): the books could not tell a condition from a case named like one; an explicit condition on every event and in every call ID keeps each cell unambiguous.
- **Limits, ranking or editions chosen by the model**: model output could widen the evidence set; fixed bounds can be tested without a model.
- **A framework harness (LangGraph, LlamaIndex) or several agents**: new dependencies and orchestration for one tool and two rounds.
- **More tools from the start**: no concrete scenario needs a second tool yet; one is added only when one does.
- **A hard wall-clock limit through a separate process or supervisor**: a new runtime harness; this increment documents the weaker, cooperative guarantee instead.
- **A separate budget for Phase 3, or a ledger per case or condition**: each new file would start from nothing and could raise the total spent; one active ledger beside the pinned historical one keeps one limit.
- **Settling error responses at zero, as Phase 2 does**: an error response reports no usage, and the agent counts only validated usage as cost, so it keeps the reservation instead.

## Consequences
- (+) Every bound, refusal and protocol rule is enforced and tested offline: the tool at its own seam, the loop at the provider's HTTP boundary with the real client, a fake key and a controllable clock ([§13](../arc42/13-test-strategy.md)).
- (+) A passage's instruction-like text reaches the model only as escaped data; offline this shows containment, not how a real model responds to it.
- (-) The passage budget equals a fixed Top-10 context in maximum distinct-passage count only, not in token volume, compute or cost; the agent adds model calls.
- (-) The deadline is cooperative, not a hard wall-clock limit: a check cannot interrupt a request already sent or a search in progress, and the HTTP client's timeouts bound each phase of a request rather than the whole, so a question can overrun its budget by the operation in progress. Stronger cancellation is open.
- (+) The spending rules are tested offline at the same seam with temporary ledgers and artifact folders: the exact admission boundary, the input cap, the dearest priced usage at the margin against its reservation, three calls of one question within the shared limit, every sent call settled once, exposure kept where usage is missing, a cost above the reservation, failed writes before and after sending (the pin, the reservation, a release and a settlement among them, simulated so that they fail the same way for any user), a concurrent invocation (also through a link to the active ledger from another folder) and a repeated one, damaged and changed books (settlements that contradict their saved usage and call IDs that do not name their case among them), altered historical bytes whatever hash the caller gives, and public records free of provider text.
- (-) The live provider contract is verified only in part, by two runs. The one-question runner (`run_question.py`, 2026-11-18, tested offline against a mocked provider) ran live once on 2026-11-20, for development case D1 with the code of `main` at `df5d20d` ([evidence](../evidence/2026-11-20-phase3-d1-agent-run.md)): two calls, both priced from their usage within their reservations, one search, ten passages supplied, a structurally accepted `partial` answer. The provider accepted what that run exercised (token counting with the tool, a strict tool beside the answer format, `tool_choice` auto with parallel tool use disabled and then `none`, a replayed thinking block before the tool result) and reported usage the validator priced, with the counted input equal to the reported input. Untested live: a third call, a second search, error responses, timeouts, the deadline paths and every path that keeps a reservation as exposure. The comparison of 2026-11-21 then ran the same loop in six agent cells and the two fixed conditions in twelve, each agent cell with two calls and one search ([evidence](../evidence/2026-11-21-phase3-E-comparison.md)); no run has made a third call or a second search. If later responses carry a usage field the validator rejects, every such call settles at its whole reservation. USD 7.060552 of the aggregate limit is committed after both runs, nothing left reserved.
- (-) The aggregate limit holds for spending through the agent's entry point, which since 2026-11-21 serves all three comparison conditions (run live once, in the comparison of 2026-11-21). The Phase 2 runner must not be used to bypass that path during Phase 3: it still checks its own ledger only, and a new Phase 2 run would change the historical ledger, after which the agent refuses to run. The limit bounds what is admitted and reserved, and the ceiling is the application's calculation from recorded prices, not a bound the provider's billing guarantees: a call costs more than its reservation only when its usage goes beyond the margin (input the count underestimated by more than 10 %) or its billing beyond `pricing.json`, and then that one call's overrun can take the total past USD 100. The books cannot be moved: another folder, a second ledger file, another limit or a lower margin is refused before anything is counted, and prices cannot be passed in. A change to `pricing.json` itself changes the ceiling, and an earlier usage settlement whose tokens the changed rates price differently then reads as damaged (its cost no longer matches its saved usage), so the agent refuses until the change is decided. The active ledger is append-only by convention: whole lines removed from its end cannot be told from the file alone, so it needs the same protection as the recorded ledger (version control).
- (-) Reservations are larger than Phase 2's for the same count (USD 0.71852 instead of 0.646604 at 1,500 counted tokens), so fewer questions are admitted near the limit. A cost above the reservation is recorded in full and stops the question; a final answer is still accepted then, so a runner must also read the flag, not only the outcome; the one-question runner reads it for every call, keeps such an answer locally and exits with a spending stop, and treats a call kept at its reservation (nothing priced) as uncertain accounting, never as success.
- (-) A write error raised only after the whole line reached the ledger (on closing the file) leaves that line in force, a truthful settlement at the calculated cost or a release of a request never sent, while the question still ends as a persistence error; a line cut short makes the ledger damaged, and every later question is refused until it is repaired by hand. Detecting the first case would need recovery logic this increment does not build.
- (-) A question whose reservation was released as never sent still has its ID in the ledger and is refused when run again; a retry, if authorised, needs a new case ID. There is no automatic recovery or retry.
- (+) The comparison is tested offline at the same seams (`test_evidence_agent.py`, `test_run_comparison.py`): A and B receive the top 5 and top 10 of one ranking as the Phase 2 request with no tool, C starts from A's request and keeps its bounds, every cell is booked under its own identity in one active ledger with each admission counting the cells before it, a repeated run under any tag or through the one-question runner sends nothing again and a stopped matrix resumes without resending, the recorded books refuse D1 under the agent and admit its other conditions, a case booked with another question or editions is refused and the comparison refuses to pair cells whose question differs or was not recorded, scoring fields are refused in the input, a matrix whose worst case does not fit is refused before the model loads and one whose rest no longer fits after another invocation's booking stops before the next cell sends, a reservation with a condition that does not record its question and editions is damage, and tests pin the stop rule (a cost above a reservation, a failed write, a refusal by the books, a call ID another case holds among them, and a call kept at its reservation stop the matrix, an unanswered cell does not) and the exit orderings a matrix produces in them (a stopped cell's 5, 6 or 3 before an unanswered cell's 4, a failed output write's 7 before a stopped cell's 5 or 6).
- (-) Code from before 2026-11-21 reads a ledger entry with a condition as damage and refuses the books (fail-closed); once a comparison or a one-question run of this code has written one, only this code or later can use them. The lock is held per cell, so another invocation could run between the cells of a case; the books stay consistent, and comparisons are run one at a time. Every cell gets the same time budget, which C shares across up to three calls and two searches, so a live run's budget must be chosen for C.
- (+) Evaluated once ([evidence](../evidence/2026-11-21-phase3-E-comparison.md)): the frozen set E1 to E6 (2026-11-21, hashes in `tools/commentary_rag/results/2026-11-21-phase3-E-freeze.json`, cases kept local) ran once under all three conditions on 2026-11-21, 18 of 18 cells answered, 24 calls settled from usage within their reservations, USD 4.569196 calculated (the plan estimated about 6.29 against a worst case of 44.352). Erhan rated the 18 answers blinded and fixed his ratings by hash before the key was opened. On the primary set E2 to E6 the agent was rated `yes` overall on 5 of 5 cases, fixed top 10 on 4 and fixed top 5 on 3; it covered 11 of 11 required claims (top 10: 10 and 1 partly; top 5: 8) and had 13 of 13 gold evidence items in context (11, 7). Against top 10 it changed the verdict on one case (E2), through the one passage its search added from outside the fixed top 10 that carries required evidence, and reached the same verdict and required-claim coverage on four (claim-level counts differ, and its E3 answer carries the one recorded error); on E1, reported apart for its overlap with D1, it alone covered both required claims. Calculated cost on E2 to E6 was of the same order for all three (agent 1.237324, top 10 1.261744, top 5 1.288300 USD).
- (-) The evaluation is small: six cases, one run per case and condition, one reviewer who also decided the cases, partial blinding (answers shown verbatim), E1 overlapping D1, and on the January-only cases fixed top 10 seeing 10 of 11 January passages. The agent searched in every cell, also where its first five passages already held all required evidence (E4, E5), so whether it can tell when not to search is untested. The conditions differ by design in system prompt, tool, calls, passages and so in token volume and cost; the comparison measures the conditions as built, not one factor at a time. With one run per cell there is no measure of run-to-run cost variation, so its cost differences (agent minus top 10: USD -0.024420 on E2 to E6, +0.101536 over all six cases) establish no repeatable advantage or penalty.
- (-) The modules reuse private helpers of the generation module (the passage renderer, the request hash), so a change there changes them; the pilot's CI job catches it. Revisit when the evaluation shows a fixed Top-10 context recovers the same evidence at lower cost, or a case needs a second tool. The first evaluation does not meet the first condition: fixed top 10 had 11 of 13 gold items in context on E2 to E6 where the agent had 13, at a calculated cost of the same order; it did reach the same verdict on four of five cases.

## Decision status
Proposed, evaluated once. The bounds, the books and the comparison worked live as decided, and the evaluation above found the agent never given a lower overall verdict than fixed top 10 and a better one on one of five primary cases, at a total cost of the same order in one run per cell. Recommendation from the AI-assisted analysis, not a decision: accept this design for seeking missing evidence (UC2), keep the fixed top 10 of ADR-025's request as the default single-call path and as the baseline, add no automatic escalation keyed on a fixed answer's status (on E1 the top-10 answer claimed `answered` while missing a required claim), and before treating the agent as a default, repeat each cell and add cases whose evidence lies beyond rank 10. Acceptance, and its scope, is Erhan's decision; until he records it, the status stays Proposed.
